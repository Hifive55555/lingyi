# 协作与合并（我们 ↔ 对面「决赛代码」）

> 场景：我们维护运行环境（小窗/部署/打包/校验），对面写战法（`Mission_all_*.py` + 任务表）。
> 两边并行改代码，定期合并。**目标：战法以对面为准，环境与链接引用以我们为准，装出来的包一定能跑。**

## 1. 仓库与分支

| 仓库 | 地址 | 说明 |
| --- | --- | --- |
| `lingyi`（唯一主仓库） | `git@github.com:Hifive55555/lingyi.git` | 根目录 = 旧仓库 `最最新代码/` 的内容 |
| 旧仓库 | 本地 `兵棋比赛智能体报告` | 历史更全（含论文、实验）；`最最新代码/` 与主仓库同步 |

| 分支 | 内容 | 规则 |
| --- | --- | --- |
| `main` | **发布版本**（能直接打包上机的那一版） | 只有发布时前进；日常**不许**直接提交 |
| `feat/<一句话>` / `fix/<一句话>` / `docs/<一句话>` | 日常开发分支 | 从 `main` 拉，改完合并回去 |
| `duimian` | 对面「决赛代码」原样快照 | **留档不删**，用于随时回看对面改了什么 |
| `legacy` | 旧仓库 118 个提交的完整历史（路径带 `最最新代码/` 前缀） | 只查不改 |

> 历史原因：早期默认分支叫 `master`，2026-11-25 已改名为 `main`。
> 老克隆里跑一次 `git branch -m master main && git fetch origin && git branch -u origin/main` 即可。

开发流程（**这是硬要求，不是建议**）：

```bash
git switch -c feat/北船打击坐标 main     # 1. 开新分支（永远从 main 拉）
# …改代码…
./verify.sh                              # 2. 必须全绿（钩子也会拦）
git commit -m "feat(红方): …"            # 3. 提交到自己的分支
git switch main && git merge --no-ff feat/北船打击坐标   # 4. 发布时再合回 main
git tag v2026.11.25 && git push origin main v2026.11.25  # 5. 打标签发布
```

**不要在 `main` 上开发**：`main` 一旦前进就意味着「这一版可以直接打包上机」。
半成品推到 main，对面拉下去就会拿到跑不起来的代码。

## 2. 双向同步（bundle 流程）

**A. 把主仓库送到对面机器**

```bash
# 本机：打一个只含 master 的包
git bundle create /tmp/lingyi.bundle --all
scp /tmp/lingyi.bundle grea@10.129.194.5:C:/Users/grea/
```

```powershell
# 对面机器：首次 clone / 之后增量 fetch
cd C:\Users\grea\Desktop
git clone C:\Users\grea\lingyi.bundle lingyi
# 增量（已有仓库）：
cd C:\Users\grea\Desktop\lingyi
git fetch C:\Users\grea\lingyi.bundle master:master
git checkout master
```

**B. 把对面的改动送回本机**

```powershell
# 对面机器：开分支 → 提交 → 打包
cd C:\Users\grea\Desktop\lingyi
git checkout -B duimian master
# …把 决赛代码 的改动落到仓库（映射见 §3）…
git add -A && git commit -m "对面版本快照：<一句话>"
git bundle create C:\Users\grea\duimian.bundle --all
```

```bash
# 本机：收包 → 取分支 → 合并
scp grea@10.129.194.5:C:/Users/grea/duimian.bundle /tmp/
git fetch /tmp/duimian.bundle duimian:duimian
git merge --no-ff duimian -m "合并：对面（决赛）版本"
```

> 若对面机器以后能上网：直接 `git remote add origin …` + `git push/pull` 即可，
> bundle 流程可以整段删掉。**bundle 只是绕开网络限制，不改变分支规则。**

判断「对面那份小窗是不是旧版」的硬办法（别靠眼睛看）：

```bash
# 比较函数名集合：如果对方是子集，说明不具备我们后来的能力
python - <<'EOF'
import re, pathlib
def defs(p):
    s = pathlib.Path(p).read_text(encoding='utf-8', errors='replace')
    return set(m.group(1) for m in re.finditer(r'^\s*def (\w+)', s, re.M))
ours, theirs = defs('小窗/overlay/agent.py'), defs('/tmp/对面/agent.py')
print('对面独有：', sorted(theirs - ours))   # 期望为空
EOF
```

2026-11-25 那次合并的结果：对面 `agent.py` 57 个函数、`launcher.py` 20 个函数，
全部是我们（64 / 31）的子集 → 小窗整块取我们的，`git diff` 逐字节一致。

## 4. 合并策略（按目录定归属）

| 目录 | 冲突时取谁 | 为什么 |
| --- | --- | --- |
| `智能体代码/Mission_all_*.py` | **对面** | 战法/任务/坐标是他们在实盘调的 |
| `智能体代码/*任务列表.xlsx`、`*总任务.txt` | **对面** | 同上；且 `pack.py` 要打进包 |
| `智能体代码/entitys/**` | **对面** | 引擎副本，跟灵弈版本对齐 |
| `智能体代码/tools/**` | **我们** | 校验工具是我们维护的（`COORD_OVERRIDES` 在这里登记） |
| `智能体代码/战术智能体说明.md` | 谁改得多取谁 | 领域说明文档，两边都可能补 |
| `小窗/**` | **我们** | WebView2 宿主、监控窗、自绘缩放、快捷方式都是我们做的 |
| `pack.py` / `deploy.ps1` / `deploy.bat` / `installer/**` | **我们** | 部署链路只维护一处 |
| `README.md` / `AGENTS.md` / `docs/**` | **我们** | 契约文档 |
| `.gitignore` | 我们（合并两边新增项） | 对面可能带进 `.venv/`、`logs/` |

**对面改了战法但没改工具时**，合并后我们这边必然会出现「`check_table` 报不一致」——
**这不是合并错**，是坐标改了表没改。处理方式：在 `tools/check_table*.py` 的
`COORD_OVERRIDES` 里登记（以代码为准）+ 写一行原因，**不要**去改 xlsx 原始表格。

## 5. 合并前的检查清单（逐条打勾）

```bash
# 1. 取到对面分支后先看差异面：应该只有战法/任务表，不该有小窗、部署脚本
git diff --stat master..duimian

# 2. 共享资产先比 md5（战术模块、xlsx、weapons.json、settings.json）
md5sum 智能体代码/BattlefieldMonitor.py …

# 3. 合并（--no-ff 保留合并点，方便回退）
git merge --no-ff duimian

# 4. 若对面覆盖了小窗：整块回退到我们的版本，并在提交信息里写函数集合证据
git checkout master^1 -- 小窗

# 5. 跑验证（全部必须绿）
python -m py_compile 智能体代码/Mission_all_red.py 智能体代码/Mission_all_blue_hh.py \
                     小窗/overlay/agent.py 小窗/overlay/launcher.py 小窗/overlay_ai.py pack.py
python 智能体代码/tools/check_table.py         # 结论: 全部一致
python 智能体代码/tools/check_table_blue.py    # 结论: 全部一致
python 智能体代码/tools/selftest_offline.py    # 全部断言通过
python 智能体代码/tools/selftest_blue_hh.py    # 全部断言通过
./pack.sh                                      # 包内 overlay_wv2.exe / 创建快捷方式 / xlsx 都在

# 6. 部署侧（有 Windows 目标机时）
#    setup.exe /SILENT  → 退出码 0
#    check_env.py        → 六项全 [OK]，退出码 0

# 7. 推送
git push origin master duimian
```

## 5.1 装了钩子就不用记命令

```bash
git config core.hooksPath .githooks     # 每个克隆做一次
```

之后 `git commit` 会自动跑 `verify.sh --quick`（`py_compile` + 任务表核对 + 打包清单），
红灯直接拦下。全量（含离线自测）仍建议手动 `./verify.sh` 再交 PR。

## 6. 对面新增文件时必须同步的三处（否则「本机能跑、装出来缺文件」）

1. `pack.py` 的 `REQUIRED` / `OPTIONAL` / `DIRS` —— 决定进不进 zip
2. `deploy.ps1` 的对应段（①~⑥）—— 决定解到目标机哪个目录
3. `tools/check_env.py` ⑤ 段 —— 决定部署后能不能自检出来

只做 1、不做 2 → 文件在包里但没落地；只做 2、不做 1 → 包里压根没有。

## 7. 历史教训（都是真实踩过的，别再犯）

| 事故 | 根因 | 现在怎么防 |
| --- | --- | --- |
| 客户端报「智能体运行异常 / `ModuleNotFoundError`」 | `agentConfig.json` 的 `filePath` 被写成相对路径，平台 `agent_path=dirname(filePath)` 退化成 `ai\agent` | 只许绝对路径；`install_agent_config.py` 不再提供 `--relative` 语义 |
| 装了包但少文件 | 父仓库 `.gitignore` 忽略 `*.xlsx`，任务表没入库，`pack.py` 却依赖它 | xlsx 已入库；`pack.py` 缺文件会报错退出 |
| 小窗灰屏 | `%LOCALAPPDATA%` 不可写，Edge `--app` / WebView2 默认 UDF 都失败 | 自带宿主 + UDF 留 exe 同级；`check_env` 缺宿主记硬失败 |
| 拖边框拖不动 / 四周白框 | 无边框窗口没有 `WS_THICKFRAME`；加上后 Win11 DWM 又画一圈白边 | 自绘缩放（`WM_NCHITTEST` + `SetBounds`），不加 `WS_THICKFRAME` |
| 监控窗每帧顺序乱跳 | 后端按 `tgo` 排序，`tgo` 每帧变 | 前端固定排序（单元按编号、弹按弹型+距离），`tgo` 只做颜色分级 |
| 安装包弹「部署好像没成功」 | 自检写在 `ssPostInstall`（`deploy.ps1` 还没跑）且路径还是老布局 | 自检改到 `deploy` 之后，且同时认 `ai\agent\` 与 `intelligent\` 两种布局 |
