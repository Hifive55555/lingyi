## 二、与讲解思路的不一致

### 2.1 定位漂移：从"实现说明"变成"规则审计"

- 讲解的组织方式：按难度递进讲五个智能体（「最简单」→「次简单」→「比较难」），每条给"触发 → 判定 → 动作 → 阈值"。
- 正式稿的组织方式：第 3 章立一个 d0 判据，第 4–9 章用它逐条审规则，第 10 章列落差。
- 后果（不是风格问题，是内容问题）：
  1. 讲解的 d0 只用于"打空战"一个智能体；正式稿把它扩成四条规则的统一判据。这个扩展是正式稿自己的贡献，但摘要写成"我队搭了五个智能体…核心结果是一个统一的判据"，读起来像讲解本来的主张。建议在摘要或 §1.2 明写"d0 的统一化是本文对讲解的推广，讲解仅将其用于空空交战"。
  2. 讲解自评"最有价值"的规则被正式稿表扬后放弃（见 2.3）。
  3. 正式稿通篇没有"我们怎么把这五条规则写成代码"的内容。评审读讲解、再读报告，会看到两个不同的东西。

### 2.2 讲解自列的 V1–V7 验证清单消失了

`docs/讲解/02-讲解语义解析.md` §6 从视频里提出 7 项明确要求（V1 躲避二维表+三维曲面、V2 追击模型"实际验证"、V3 反解最优开火距离并拟合、V4 成套逻辑在不同弹速下的成功率、V5 一敌一我跑多遍、V6 高度差幅度、V7 报告用图）。

- `docs/粗版报告.md:408-421` 有一张完整的 V1–V7 对应表（V1–V7 全部 ✅）。
- 正式稿把这张表删了，没有任何章节说明"讲解要的七件事我们做了哪几件"。
- 结果是：读者无法判断报告的实验覆盖了讲解的哪些诉求。其中 **V3（反解最优开火距离并拟合曲线）在正式稿里实际没有做**——`fig3` 的 (c) 是命中率与先射时间，不是"最优 d 随弹速的曲线"。粗版报告标 ✅ 属于过度声明，正式稿删表时把这个缺口一起藏了。

建议：恢复一张 V1–V7 对应表（放 §9 末或附录 B 前），诚实标注 V3 未做。

### 2.3 讲解里最有价值的一条规则，只被表扬、没有被建模

`main.typ:312` 自己写着：158C 需要对方飞机持续照射，"这条规则把一个'防御'问题转化成了'夺取局部制空'的问题，**是全部规则里思路上最有价值的一条**"。然后呢：

- 第 6 章只做了一次弹舱/拦截距离的蒙特卡洛（方案 R/B1/B2/B3），**没有任何一处建模照射链**。
- 而这条恰恰是最容易做的：把 158C 的命中概率写成"照射机存活且在位"的函数，比较"只关雷达背身跑"与"关雷达 + 召苏-57 驱离照射机"两种处置的期望拦截率。三五十行代码，正好符合"受控对比"的既有范式。

现在报告的结构是：用一整章证明"分层补射不是效率最优"，却把讲解自己认为最有价值、且正式稿也认同最有价值的那条规则留在定性描述里。这是最大的一处"讲讲解的思路、却没有沿讲解的思路做"。

### 2.4 地导营"前两条没有可检验的内容"——与第 2 章自相矛盾

- `main.typ:377`："前两条没有可检验的内容（讲解对'停车'未给时机与判据）"，即"关雷达 + 加速跑"与"开雷达 + 自由开火"都不检验。
- 但 `main.typ:129-131` 刚说过："开雷达提高探测能力的同时也提高被反辐射武器锁定的概率，这正是船只自卫第三条规则（时开时关雷达）的物理基础。"

同一机理，在第 2 章被当作物理基础，在第 7 章被宣布为不可检验。而想定里红方就有苏-30SM 挂 Kh-31P 反辐射弹（代码 `[RED]:420-424` 的挂载表），地导营"被打就关雷达"完全可以在现有运动学核心里加一个"雷达开机 → 反辐射弹锁定概率上升"的简单项来检验。这是低成本、高相关度、且能直接回应讲解的一条。

### 2.5 监控"指向判定"被判"没实现"，也没有替它做一个最小实现

- 正式稿 `tab:inconsistency` 写"监控输出：只有类型/距离/航向，无弹速"——准确。
- 但样例代码 `[RF]:164-196` 实现了讲解所说"计算指向自己的弹"的**最小可行版本**：Type==1 的接触、距离 ≤100 km、`bearing_to_aircraft` 与 `CurrentHeading` 夹角 ≤20°、取最近一个。这正是 L1 里讲解说"我没有实现"的那件事的一半。
- 正式稿第 2 章说"所有下游的判断质量都被监控的输出上限锁死"，这是一个**可以量化**的断言，但没有任何实验。用现有仿真加一组"信息降级"消融（弹型+弹速 / 只有弹速 / 只有距离+航向）就能回答：监控少给一个字段，下游存活率掉多少。这既补上第 2 章的断言，也直接回应 L1。

### 2.6 船只自卫：漏掉讲解的真实机理，结论因此偏硬

讲解对"ABDE 区用 MAX D 开火"的理由是**射击轮次**，不是命中概率：

> 〔00:08:49〕它原本比如说是二分之一 D 开火 → 〔00:08:52〕那它最多开三轮 → 〔00:08:53〕我们最远设置我们就开五轮

- 正式稿 `exp_c`（`paper/scripts/comparative.py:280-330`）里每舰每层只打一发，**没有射击轮次机制**，因此"MAX D 开火能多打两轮"这一讲解机理在模型里根本不存在。
- 但第 7 章（`exp_d`）却建了轮次：`salvos = max(1, min(2, int((d_fire-15)/10)+1))`。同一类机理，第 7 章用了、第 6 章没用，两章结论方向相反，读者会困惑。
- 正式稿的对比方案「双舰均在半射程开火」（B3）是讲解**从未提出**的方案。它是合法的对照，但 `main.typ:334-353` 的措辞"讲解主张的方案并不优于…"容易被读成"讲解的方案被推翻"，实际是"讲解没考虑的另一个方案更好"。
- 更关键：结论完全由自设的 `pk(d)` 曲线（Dmax 处 0.35 → 零距离 0.90，单调递减）决定。`pk(d)` 单调递减意味着远界射击在任何情况下都是亏的，结论几乎是假设的同义反复。报告没有对这条曲线做敏感性分析（`exp_e` 只扫了躲避和地导，没扫舰空 `pk(d)`）。
- 附带：仓库里两份实验对同一方案的数不一致也没交代——`docs/实验/e5_ship.csv` 的「S3 双船分层」= 0.7612（100 轮），`paper/data/c_ship_scheme.csv` 的「R 双船分层」= 0.7512（200 轮）。粗版报告当时结论是"分层全面最优、唯一与讲解同向"。

建议：给 `exp_c` 加上与 `exp_d` 同构的轮次机制（`Dmax` 开火可 5 轮、`½Dmax` 可 3 轮，与讲解原话一致），再扫 `pk(d)` 斜率，然后重写 §6.3 的三条结论。

### 3.4 "综合概率随开火距离单调下降"与自家数据矛盾

`main.typ:381` 与 `fig4` 的 (b) 面板标题（`figures.py:374` "地导开火时机：概率随距离单调下降"）都这么写。`paper/data/d_sam_opening.csv` 的 `p_total`：

```
0.2 → 0.9365   0.3 → 0.9807   0.4 → 0.9480   0.5 → 0.9616   0.6 → 0.9154
0.7 → 0.8480   0.8 → 0.7382   0.9 → 0.5684   1.0 → 0.0000
```

0.2→0.3 上升、0.4→0.5 上升，两次非单调。原因是 `exp_d` 里 `salvos` 是个手写的阶梯函数：`salvos = max(1, min(2, int((d_fire-15)/10)+1))`，只有 `d_fire < 25 km` 时才是 1 轮，其余恒为 2 轮。

这条不是文字问题：**第 7 章"3/5 Dmax 不是最优点、0.3 Dmax 才是（0.981）"这个结论，完全由这个阶梯函数和 `salvos` 上限 2 产生**。若把轮次改成随距离单调增加（物理上更合理：越早开火，可安排的射击轮次越多），远界开火的优势会重新出现。这正是讲解"5 轮 vs 3 轮"的逻辑。

建议：(a) 改掉"单调下降"的措辞；(b) 把 `salvos` 的构造写进正文与附录 A；(c) 对 `salvos` 规则做一次敏感性，或直接按"每 X 秒一轮"重做；(d) 结论改写成"在轮次上限为 2 的假设下…"。

## 四、实际代码里有价值、但报告一处都没挖的部分

先说定位问题。`main.typ:87` 引用队内 `README.md`（"最终的报告不参考实际的实现…代码的作用是提供灵弈系统的结构示例"），据此把代码限定为"阈值核对工具"。这个引用是准确的，但**结论过度**：

- README 说的是"报告的**说法**遵从讲解"，不是"报告的工程事实不许用代码"。阈值核对本身就是"用代码"。
- 内部文档 `docs/资料/04-代码结构映射.md` §6 的"可复用代码片段"表里，作者自己标了两条"**可作为'工程约束'章节素材**""**报告可放附录**"（指令配额、BOL 闭环），正式稿一条都没采纳。

以下 8 块内容都在 04 文里点过名或可 grep 到，且都能直接补强现有章节。

### 4.2 `_OrderBudget`：滚动窗口节流（`[RED]:102-210`、`2626-2667`；`[BLUE]:89-193`）

值得写的原因不是"我们做了限流"，而是它暴露了平台的一个非显然行为：**超限的指令是被静默丢弃的**（平台回"智能体指令条数超出数量限制，已被取消下发"），现象是"设了却没生效"的随机丢包。因此一个下发 450–520 条开局指令的智能体必须自己节流。

实现里有三个不平凡的细节：

1. 双预算：每周期硬上限 400（`CYCLE_ORDER_BUDGET`）+ 跨周期滚动 10 秒窗口 460。只做前者不够，因为推演跑得快时多个决策周期会挤进同一个 10 秒窗口（`[RED]:112-116` 注释）。
2. 超窗口时 `sleep` 到最早那批滑出窗口再发，而不是丢包；同时给单次睡眠（15 s）与单周期累计睡眠（12 s）设上限，避免战前规划窗口被睡穿。
3. **新建出来的任务对象要把 `_game_server` 重绑到计数器上**（`[RED]:201-207`、`:2640-2667`），否则任务级条令的调用会绕过计数。这一条是纯粹的经验产物，任何读代码的人都不会第一次想到。

这一段能填掉正式稿 §2.3 现在的那段错论证，而且能解释一个真实的架构后果：**开局一次性下发 450–520 条指令（条令 + 挂载 + 31 个任务 + 航线）→ 智能体的重心被迫前移到 `initial()`，`step()` 只剩兜底**（`[RED]:2774-2811` 只做 BOL 重试与航路兜底）。

### 4.3 「成功≠生效」的闭环核对 + 5 级降级（`[RED]:2215-2390`）

这是整个代码库最有价值、也最适合进报告的一段，正式稿零提及。

问题：平台对 `attack_BOL` 回 `code==0`（"指令执行成功"），但**可能一发弹都没出筒**。代码的应对：

1. 下发前记下弹药数 `before = _count_weapons(...)`；
2. 下一周期核对 `cur < before` 才算真打出去，否则给 1 个周期的宽限（`wait < 2`）；
3. 若弹药没动，换下一种下发方式，共 5 级：带航迹点 → 不带航迹点 → 封装接口 `attack_BOL` → 只发 1 发 → 挂架传 0（`BOL_STRATEGIES`）；
4. 5 级都失败才放弃，并把**平台回复原文**写进 error 日志。

这段可以抽象成一句可推广的结论：*在"接口返回成功"与"世界状态改变"之间必须有一道核对*。它同时是正式稿 §2.3 想说的"动作生效存在延迟"的硬证据——只不过真实的延迟不是几毫秒，而是"1 个决策周期 + 可能永久失败"。

### 4.5 名称 / ID 解析层：换想定不失配（`[RED]:215-269`、`849-896`、`1048-1183`）

- `_sel(key, *nums)`：选择器 DSL，关键字任一命中 + 舷号（支持 `'1-6'` 区间）→ `{'keys':(...), 'nums':(...)}`。
- `_norm(text)`：归一化——小写、去空白/引号/括号/全半角标点/`-` `.` `/`，使"苏-27SM/SM3型战斗机#1"与"苏27SM SM3 型战斗机 #1"命中同一关键字。
- `_unit_num(name)`：取 `#n`，取不到退回结尾数字。
- `_resolve_units`：先严格匹配"关键字 + 舷号"，否则唯一命中兜底。
- **挂载不写死 ID**：`_loadout_rows(aircraft_dbid)` 从 `model.db` 现场查该机型可用挂载，`_pick_loadout` 按"挂载名须同时包含全部关键字"挑一条（`[RED]:1048-1183`，22 组机型）。
- 武器 DBID 对不上时按武器名关键字兜底（`_find_weapons_by_name`，`[RED]:1960-1992`）。

对照：官方样例 `[R4]:26-59` 是硬编码 `dbid → loadout_id` 表。这一条差别值得写成一句方法论——*规则型智能体的可移植性不来自规则本身，来自"永不写死 ID"这一层*。而正式稿第 10 章恰好只说"讲解的数字在代码里都不存在"，把代码里真正做对的事漏掉了。

### 4.6 状态机、优先级与配额簿记（样例 `[RF]:58-150`）

正式稿 §2.3 断言"没有一条需要记住上一步做了什么"，`[RF]` 的实际实现正好相反，而且每一步都有理由：

- **优先级阶梯**：生存（规避）优先于进攻。规避时一次性把状态切到位：`weapon_control_status_air(Hold)`、`ignore_plotted_course(No)`、`EMCON_Obey_doctrine(False)`、`switch_radar(False)`，并且**把已分配的目标释放掉**（`pop` 并回退 `target_assignment_counts`）。
- 这条释放是必需的：WTA 是"每目标最多 2 架"，一架被逼进入规避却不释放配额，另一个目标就永远等不到第二架。正式稿第 6 章讨论的是"火力分配的概率模型"，完全没有触及真实实现里这个**配额簿记泄漏**问题。
- **转弯方向取短边**：`notch_ward = 1 if bearing_to_aircraft - missile_heading > 0 else -1`，然后 `evasion_heading = bearing + notch_ward * 90`。这就是讲解"3-9 方向、左右扭"落到代码上的样子，而且选的是**转向代价小的一侧**。
  对照：正式稿的仿真 `comparative.py:118` 是 `side = 1.0 if rng.random() < 0.5 else -1.0`——**随机选边**。0.645/0.781 这两个数里有随机选边带来的损失，报告没有声明。这是一个可以直接改一行、然后重跑的偏差来源。

### 4.7 人机协同接口（唯一能撑起"人机协同"标题的素材）

- `[BLUE]:1768-1815` `watch_mission_release`：监听"某单元上一周期有 `AssignedMission`、本周期变空"→ 清残留航路 + 速度 0 + `Throttle.FullStop`，然后**退出干预**（"之后你手动分配任务或画航线，智能体都不再干预"）。这是"人接管 → 智能体让位"的显式协议。
- `[RED]:1184-1208`：雷鸣号 7 艘对空条令改"限制开火（仅手动）"——把开火权交还给人，因为讲解里"有弹就开雷达打、没弹就时开时关"依赖人的临场判断。
- `[BLUE]:1576-1610` `rush_ships`、`:1611-1650` `move_ground_units`：全速集结、装甲车分组最大速度开进——纯"执行人的决心"的一类动作。
- `[RED]:2215` 的日志策略（每次下发都记录"平台回复原文"、`agent_message_text` 输出 `[WTA] 正在锁定…`）也是给人看的：人要从界面上知道智能体在干什么。

这四条合起来就是一份"人机协同分工表"：智能体做连续/机械/时间敏感的（规避、配额、核对），人做需要意图的（任务分配、开火授权、临机改航）。这正是赛题要求、也是正式稿标题承诺而正文缺失的东西。

### 4.8 经验 Pk 模型与威胁度模型：可给正式稿的自设参数找一个外部锚点

正式稿第 7 章自己造了一个单发杀伤概率：`p_single = min(1, (V_end - V_term)/(0.6 V_0))`（`comparative.py` 里叫 `margin`），并声明"全部参数由我们设定，无外部来源"。

样例代码里已经有一套现成的经验模型（`calculate_weapon_attack_air_rate.py`，169 行，红蓝同源）：

- 射程比例衰减：`propulsion_rate` 0.5 / 0.75（超过某比例后线性衰减）；
- 目标速度惩罚：按 target/self 速度比 4 档（0.8 / 0.7 / 0.6 / 0.5）；
- 机敏度惩罚：`attack_rate -= actual_agility * 10`，并对高空（>3000 m）衰减、对载重 `0.4a + 0.6a(1-weight)`、对熟练度 0–4 级乘 0.3/0.5/0.8/1.0/1.2；
- 掠海高度惩罚：按 91.44 / 60.96 / 30.48 m 三档扣 5/15/30。

威胁度侧还有 5 因子加权（类型 0.3 / 距离 0.25 / 航向 0.2 / 速度 0.1 / 高度 0.1，`calculate_threat_level_of_the_target.py:19-23`），其中高度威胁用的是 **±3000 m 绝对差**，而讲解要求 90%–120% 相对容差（这是 `tab:inconsistency` 第 14 行）。

三条用法：

1. 用这套经验曲线替代/校核自设的 `p_single`，第 7 章"3/5 Dmax"的结论会有一个非自设的锚点；
2. §5.3"高低差：比能量"（$2g\Delta h$）现在只与讲解的 90%–120% 对照，可以再加一列"样例代码的 ±3000 m 绝对差"做三方对照——正好是"讲解 / 代码 / 物理"三把尺子，与全文的证据分级框架一致；
3. `[THREAT]:69` 把 key 拼成 `'uknown'`（应为 `'unknown'`）导致"未知类型"永远落到兜底 `50000`；`:51` 千米→海里用 `1.825`（应为 `1.852`）。这两条 `docs/资料/04` 已记录，正式稿完全没提——它们恰好能支撑"阈值拍脑袋"这个全文主题，而且比"讲解的数字不存在"更有说服力，因为这是**在跑的代码里的**错误。
