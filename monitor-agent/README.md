# 监控智能体（monitor-agent）

检测**我方每一个单元是否正被敌方弹药朝我飞来**，报出**指向它的那枚弹的型号与当前弹速**，
并在叠在灵弈客户端上的小窗里**按 空 / 海 / 陆 三组**展示。

**只算、不动手**：不下发任何一条指令（不调 `attack_*` / `set_*` / `plotted_course` /
`withdraw_from_mission`）。所以不需要 zmq 收发锁、不会和 step 线程抢口，
可以和 `Mission_all_red.py`、`Mission_tactics_red.py` **同时导入、同时启动**而互不干扰。

判定口径：**不设距离 / 时间 / CPA 门限，弹在朝我飞就算**（对方弹射程未知，保险起见）。

- 给其他智能体调用的接口说明 → **[`API.md`](API.md)**
- 本文讲：部署、原理、频率、小窗。

## 2. 实现方式：原理与数据来源

### 2.1 平台没有“我被瞄准了”这个字段

`THSideInfo` / 情报 `THContactInfo` 里都没有“锁定”标志，只能自己用几何算。输入只有两样：

| 数据 | 从哪拿 | 用到的字段 |
| --- | --- | --- |
| **敌方弹药** | `situation[1]`（情报 dict），退化取 `self.Contacts` | `Name`(弹型)、`DBID`、`Type`、`Lat/Lon`、`CurrentHeading`、**`CurrentSpeed`(弹速)** |
| **我方单元** | `self.aircrafts` / `self.ships` / `self.submarines` / `self.facilitys` | `Name`、`Lat/Lon`、`CurrentHeading`、`CurrentSpeed`、`CurrentAltitude`、`DamagePercent` |

弹药识别：`Type == 1`（`ContactType.Missile`）；有些版本把在飞弹药记成 `Type=0`，
另按名字兜底（`导弹 / missile / AGM- / Kh- / SS-N / 锆石 …`）。

分组：`aircrafts → 空`、`ships + submarines → 海`、`facilitys → 陆`。

### 2.2 判定：相对运动的最近接近点（CPA），**朝我就算**

```
r  = 弹位置 − 我位置（km，rx 东 / ry 北）
v  = 弹速度矢量 − 我速度矢量（km/h）
t* = −(r·v)/|v|²          # 到最近接近点的时刻（小时）
CPA = |r + v·t*|          # 最近接近距离
tgo = t* × 3600           # 预计到最近接近点的时间（秒）
判定：t* > 0（还在靠近）→ 这枚弹朝我来
```

不设距离 / 时间 / CPA 门限。需要收紧时 `Monitor(self, gate={'cpa_km':3,'max_km':90,'tgo_s':900})`。

> 只在“情报没给 `CurrentHeading`”时才退化：用上一周期同一（单元, 弹）的距离差判断是否在收缩，
> `tgo ≈ dist/rate`；第一次见到这枚弹时不判（宁漏一周期，不误报）。

### 2.3 量纲：`CurrentSpeed` 是**节**，不是 km/h

`entitys/unit.py:88` 写明“当前速度 海里/小时”。本模块入口统一 `×1.852` 换算成 km/h，
对外所有弹速都是 km/h，与报告里 2500 / 1500 km/h 的阈值同口径。
（旧 `Mission_tactics_red._cpa()` 直接把节当 km/h 用，几何上偏了 1.852 倍。）

### 2.4 输出

每个单元一行，`ms` 是按 `tgo` 升序的来袭弹列表（小窗展示最多 8 枚）：

```json
{"id":"…","n":"苏-35S #1","g":"air","hit":true,"n_ms":2,
 "ms":[{"id":"…","n":"AGM-88E","db":2056,"spd":2963,"d":7.9,"cpa":2.3,"tgo":6}, …]}
```

`spd` 是**当前弹速 km/h**（按你的要求只显示当前值，不再区分“观测最高速”）。

## 3. 监控频率

| 层级 | 频率 | 说明 |
| --- | --- | --- |
| **判定** | `DECISION_SEC = 5` 推演秒 | 平台在 `step()` 里按决策间隔调用；5 s 是比赛规则允许的最小值（附件2：5 倍速 ↔ 最小 5 秒）。改这个常量即可调 |
| **小窗推送** | 每个 step 一次 | 10 倍速时 ≈ 每 0.5 s 墙钟 |
| **心跳重建** | 每 3 s 至少一次 | `SnapServer._beat` 线程：推演暂停/战前 step 不来时用缓存重建快照，小窗不会误判“没对局” |
| **页面渲染** | 收到即重绘 | 保留滚动位置，不打断正在输入的搜索框 |

成本：一次 `单元数 × 弹数` 次 CPA，单次约 10 µs；200 单元 × 60 枚 ≈ **2.2 ms**，
占 5 s 决策预算的 0.04%。本智能体不下发指令，**不消耗** 500 条/10 s 的指令配额。

## 4. 小窗的实现方式

三层，和「灵弈小窗」同一套思路（代码、端口独立）：

```
① lymonitor/agent.py  在客户端进程里      ── WebSocket 127.0.0.1:8762/ws ──┐
   step() 算完 publish()，序列化成一行 JSON                            │
                                                                      │
② lymonitor/web/      静态页面（HTML+JS）  ◀── HTTP 127.0.0.1:8763 ─────┤
   monitor.js 连 ① 的 WS，收到快照整块重绘                             │
                                                                      │
③ launcher.py         独立进程：起 ②，用 Edge/Chrome --app 开一个无框 ──┘
   小窗（520×900，屏右侧），每 0.25 s 检查是否被全屏客户端盖住，
   盖住就 SetWindowPos(HWND_TOPMOST) 重新置顶
```

技术要点（都是踩过的坑）：

- **WebSocket 而不是轮询**：每客户端一个 `asyncio.Event` + 发送协程，`publish()` 只改一个字符串再
  `set()`，`call_soon_threadsafe` 跨线程调度，不阻塞 step 线程。
- **心跳**：`_sender` 3 秒没东西发就发 `{"type":"hb"}`；页面侧 8 秒收不到就当掉线，1.5 秒重连。
- **置顶**：`HWND_TOPMOST` 必须按**指针**传（`wt.HWND(-1)`），按 int 传会被截成 `0xFFFFFFFF` 失效；
  用 `GetWindow(hwnd, GW_HWNDPREV)` 沿 z 序找“盖住我的窗口”，比定时无脑置顶省 CPU。
- **页面缓存**：`/web/monitor.js?v=<mtime>` 做版本号，改完刷新即生效。

页面布局（三组竖向堆叠，组标题粘性）：

```
┌ 监控 红方  00:12:30   被攻击 5 / 46   敌方弹药 12        ● 监控中 ┐
│ [只看被攻击] [按弹速排]  搜单元（苏35 / #1）                      │
├───────────────────────────────────────────────────────────────┤
│ 空  被攻击 2 / 18                                              │
│  苏-35S #1  8km  ┃AGM-88E 2963km/h 8km 6s┃Kh-31P 1667km/h 55km 118s│
│  苏-27 #3                                                      │
│ 海  被攻击 1 / 24                                              │
│  雷鸣号 #1       ┃SS-N-33 907km/h 33km 134s┃                   │
│ 陆  被攻击 0 / 4                                               │
└───────────────────────────────────────────────────────────────┘
```

- 每个单元一行，后面跟**指向它的每一枚弹**一个块：`弹型 | 当前弹速 km/h | 距离 km | 剩余秒`
- 左边框按紧急度着色：`tgo≤30s` 红 / `≤90s` 橙 / 其余黄 / 算不出时间灰
- 悬停看 `当前弹速（km/h 与节）· 当前距离 · 最近接近 · 预计到最近接近点`
- 被攻击行高亮，“只看被攻击”时隐藏安全行；点组标题折叠
- 组标题 `被攻击 x / 总数 y`；顶栏 `被攻击 5 / 46`、`敌方弹药 12`

## 4.5 无头引擎实测（2026-11-17，真实平台数据）

不是离线自测，是在 `Plat.exe` 无头引擎里跑真对局（Session 1 计划任务投递），
监控智能体作为红方唯一规则智能体、蓝方挂一个“打手”逼出来袭弹：

| 想定 | 步数 | 墙钟 | 我方单元 | 峰值弹药 | 被攻击峰值 | 弹速范围 | 异常 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 海洋空战 | 400 | 90 s | 8（空6/海2/陆0） | 0 | 0/0/0 | — | 0 |
| 海洋空战（含蓝方打手） | 400 | 90 s | 8 | 0 | 0/0/0 | — | 0 |
| 诺曼底2027(人机协同-人机版V0.2.7) | 300 | 86 s | 138（空91/海20/陆27） | **31** | 81/19/27 | **352–4908 km/h** | 0 |

- 分组完全正确：`aircrafts=91 / ships 19+submarines 1=20 / facilitys=27`。
- 弹速 352–4908 km/h（4908 ≈ 2650 节），**证明节→km/h 的换算是对的**。
- 小窗 WebSocket 在真实引擎进程里打通：单帧 **79 KB**、138 行、6 枚弹、组统计正确。
- 平台上的弹名是 `防空导弹#40`（db=890）这种；同时还会混进 `警告来袭#70` 一类
  **告警情报（也是 Type=1）**。若确认二者是同一件事的两种表示，把
  `Monitor.IGNORE_NAME_KEYS = ('警告来袭',)` 填上即可去重。

### 无头实测暴露并修掉的 4 个真问题

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 智能体只跑几十步就被当“已结束” | `MonitorAgent` 继承的是 `Player`，缺 `is_done/deduction_end` | 改继承 **`RuleAgentBase`** |
| 2 | 一局直接终止、日志报“智能体初始化代码出错” | 平台的 step 里**抛异常 = 致命** | `step()` 整个函数体 try/except 兜住 |
| 3 | 把 `DDG 113“约翰.芬”阿利伯克级 Flight IIA **导弹**驱逐舰` 判成来袭弹 | 名字兜底里有裸 `'导弹'`，把军舰一起匹配了 | 加平台词黑名单（舰/船/艇/机/基地/雷达/营…），并改为只认具体弹型关键字 |
| 4 | 速度恒为 0 的杂项情报被当成弹（`tgo` 乱掉） | 没有速度下限 | 加 `MIN_MISSILE_KMH = 50` |

### 客户端挂载路径（`main.py` + `config/monitor_ai#1`）复查修掉的 5 处

这条路是「智能体调度 → 启动」真正走的（客户端为每个智能体 spawn
`python main.py config/<名>#1`），现场实测 `own=126 / groups 空80-海19-陆27` 数据正常，
但代码审查 + 复查又发现 5 处：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 5 | `Monitor.rows()` 是**浅拷贝**，`_build()` 为了限宽截断 `r['ms']` 会改到监控内部的同一批 dict | 一个单元被 **>8 枚弹**指着时，`threats_for()` / `incoming_list()` 会**凭空少掉几枚** | `rows()` / `threats_for()` / `missiles()` 一律返回深一层副本 |
| 6 | `ensure()` 只看 `situation` 的**对象身份** | 平台的 `Player.get_situation()` 会缓存复用同一个 tuple → 监控**永久不再重算** | 改成按“推演时刻变没变”判断，时间拿不到才退回身份比较 |
| 7 | 无航向兜底里 `dt = now - prev_time` 可能 ≤ 0 | 算出天文数字的 `tgo`，排序被顶到最前 | `dt <= 0` 时给 `tgo=None`（未知），不猜 |
| 8 | 弹名兜底 `'弹%s' % db` | 情报没 `DBID` 时显示 `弹None` | 依次退 `Name → 弹<DBID> → 未知弹` |
| 9 | 开局/运行中**没有任何健康输出** | 没法判断“智能体是不是活着、有没有算”（现场就吃过这个亏） | `initial()` 打一行自检 + 每 20 周期一行 `周期N 我方/弹药/被攻击` |

另外两个顺手加的：

- **门限可用环境变量覆盖**，客户端里不用改代码：`LY_MONITOR_CPA_RATIO=0.2` /
  `LY_MONITOR_CPA_KM=3` / `LY_MONITOR_MAX_KM=150` / `LY_MONITOR_TGO_S=900`。
- 小窗每行显示**已受损百分比**（`r.dmg` 早就在快照里，之前没用上）。

## 6. 已知限制与取舍

1. **不设门限的代价（已实测量化）**：诺曼底 138 个单元的想定里，只要场上有几枚防空导弹在飞，
   **91 架飞机 / 20 艘舰船 / 27 个地面单元全部**被标成“被攻击”——因为一枚向北飞的弹，
   “朝”它前方的几乎所有单元。做展示没问题；做决策必须收紧，建议
   `gate={'cpa_ratio': 0.2}`（CPA ≤ 当前距离的 20%）或 `{'cpa_km': 3, 'max_km': 90}`。
   参考方案里还记过一个更严重的后果：判据太宽松会让“地空导弹连一直逃跑、永远不恢复”。详见 `API.md` §5。
2. **只看得到“已探测到的弹”**。情报刷新周期由平台决定，比真实弹道滞后一个情报周期。
3. **`t* > 0` 会漏掉“此刻恰好正横”的弹**（`t*` 正好 0）。实际弹道几乎不会停在这一点。
4. **不判断“这枚弹是不是我方打出去的”**。若某型弹敌我通用，可能被我方弹误报。
5. **只做展示 / 供数，不做决策**。接下游时复用 `Monitor` 的公开接口，不要自己去读小窗 JSON。
