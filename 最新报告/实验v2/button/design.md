# 设计说明：低空导弹二态按钮（一页纸）

## 1. 二态语义：把人能判断的事收成一个开关

低空导弹单元（如 `捷羚地空导弹排#1`）在同一局里只有两种"活得下去"的姿态：

| | 打击模式 `strike` | 前进模式 `move` |
| --- | --- | --- |
| 一句话 | 停车、开雷达、等目标进 0.6·Dmax 发弹 | 向正北全速机动、关雷达、不交战 |
| 平台动作 | 清航路 → 保持阵位 → 速度 0 → 油门 FullStop → 开雷达（条令层 + 传感器层） | 关雷达（同上两层）→ 松阵位 → 正北 50 km 航路 → 油门 Full/期望 50 km/h |
| 暴露面 | 高：持续辐射 + 位置固定 | 低：静默 + 移动，反辐射弹失去目标 |
| 代价 | 被反辐射弹锁定的概率最高 | 打不了任何东西，退出拦截线 |

两态之间**没有第三种**：不做"边走边打"、不做"半开雷达"。原因是这条单元的全部
生存逻辑就是一个暴露—隐藏的权衡，中间态既拿不到探测也躲不开反辐射弹，纯属把
两种代价都付一遍。二态还把"人要不要干预"变成一个**布尔决定**，与推演的 10 倍速
（180 分钟想定 = 18 分钟墙钟）相匹配：一次点击 ≈ 0.6 秒，而任何需要"读三个字段再
算阈值"的判断在这里都做不完。

二态是**姿态**，不是**动作**：点完之后状态一直保持，直到下一次点击。所以一次点击
≈ 6~7 条平台指令（清航路、停车、保持阵位、雷达 ×2、航路点、油门、速度），
而不是一次性的指令序列——这也让"一次按钮 = 多少条手工指令"可数。

上位条令不动：受到攻击时忽略电磁管控 = 否、自由开火、自动规避 = 否。本模块不改
任何条令字段，只下发单元级动作。所以"雷达关掉之后被打"这件事仍然是平台的条令
行为（该关就关、该不自卫就不自卫），人的开关只决定**当前处于哪一端**。

## 2. 为什么人只该决定"暴露 / 隐蔽"

设计报告 1.2.1 把两类失效画成互为反面：人单独做的失效是"漏"与"不一致"——
上百条配置漏一条不报错，3 秒墙钟内做不完阈值判定；智能体单独做的失效是
"不知道要什么"——它只能判定可量化的量（距离、弹速、余弹），而"这个单元现在该
藏还是该露"取决于指挥员对整体态势的判断（哪条轴线要放弃、哪次突击值得用防空
暴露换），没有可计算判据。

于是分工就落在这条缝上：

- **人**：只给"暴露/隐蔽"这一位意图。它不可量化，但人一眼就能定；
- **机**：把这一位展开成可执行、可重复、可核验的动作序列，并保证顺序正确
  （先清航路再停车、先关雷达再走）、并保证状态不被平台/条令悄悄改回去
  （每 20 个周期雷达自愈一次）。

反过来说，如果把这个决策留给智能体，规则只能写成"被瞄准就关雷达跑"——这正是
`SamBattalionDefense` 的第一版行为，在判据宽松时表现为"整局一直逃跑、再也不开
雷达"（其代码注释记录了这次实测）。人的那一句话（"现在该藏"）恰好补上了规则最
缺的那一位信息。

## 3. 与 1.3 节「意图—执行」环的对应

报告 1.3.1 的链路是：**小窗封装按钮 → 监听智能体（专用端口）→ 内核对控制流的旁路**。
本实现逐条对应：

| 报告 1.3.1 的说法 | 本实现的落点 |
| --- | --- |
| 人的指令不经界面逐条点选，而从封装按钮发出 | 页面上只有两个按钮，无自由输入（`pi_button_server.py`） |
| 监听智能体只做三件事：接收、校验、转译 | `_read_new_lines()`（接收）→ `action`/`unit` 校验 + 候选名回执（校验）→ `_posture_strike/_posture_move`（转译） |
| 它不做任何战术判断，因此不需要理解任何一条规则 | 全文件不含目标选择、威胁判定、开火决策；0.6·Dmax 只写进回执 `note` |
| 控制流旁路后端，与"看"分开 | 按钮走本地文件通道（cmd/ack），不经态势后端；页面只读自己写过的回执 |
| 与战术智能体共用 500 条/10 秒配额，所以必须去重与排队 | 一次点击只下发一次、页面 500 ms 合并重复点击、`seq` 幂等；积压按周期排队（一条一次） |
| 封装成按钮是为了让指令"可计数、可去重" | `ack.jsonl` 一行一次点击，`len(orders)` 就是指令条数 |

时序（一次点击的三个时刻）：

```
t_wall_press ──wait_ms──▶ 决策周期边界（读命令）──apply_ms──▶ t_wall_ack
     │                         │                                 │
  页面写入              幂等检查 + 解决单元名              逐条下发 + 写回执
  latency_ms = wait_ms + apply_ms
  排队下限 = 决策间隔 / 倍速（5 s / 10 = 500 ms）
  链路本身的开销 = apply_ms（这才是本设计要证明的数）
```

与报告的**一处有意的偏离**：报告写"监听智能体持有独立工作线程，不阻塞推演推进
线程"；本实现把读文件与下发都放在 `step` 线程里。理由是平台指令发送通道由战术
智能体与监听智能体共用，另起线程去发有抢占风险（未验证），而一次姿态只有 6~7 条
指令、`apply_ms` 实测应在毫秒级。代价是时延下限被决策间隔锁住——这正是为什么
`ack.jsonl` 要把 `wait_ms` 与 `apply_ms` 分开记：报告里能站得住的结论只应该用
后者，前者是采样率，不是链路能力。

## 4. 验收指标

| 指标 | 定义 | 数据来源 / 算法 |
| --- | --- | --- |
| **往返时延 P50 / P95** | 一次点击从按下到"平台指令全部下发完"的墙钟时间 | `ack.jsonl` 的 `latency_ms` 取分位数（线性插值）；同时报 `wait_ms`/`apply_ms` 分解。样本 = 点击次数；每组 ≥ 30 次才有意义 |
| **单位暴露时长** | 某单元处于"雷达开 + 静止"状态的累计推演时长 | `ack.jsonl` 按单元把 `strike`/`move` 事件排成时间轴（`sim_t`），相邻两行的 `sim_t` 差即一段持续时长；跨局按局聚合并给均值/中位数。**假设**：两次点击之间姿态不变（`REASSERT_CYCLES` 自愈不改语义） |
| **被反辐射弹命中率** | 该单元在整个对局里被反辐射弹命中的次数 / 被瞄准的次数 | 需另挂 monitor-agent 的 `Monitor` 组件记"被瞄准"（它只读、不占指令配额）；"命中"从平台推演结果/录像统计。**本模块不产生这项数据**，只能给"暴露时长"这一侧的解释变量 |
| **操作次数** | 一次姿态切换：按钮 = 1 次点击 / N 条指令；手工 = 6~7 次点选 | `ack.jsonl` 行数 vs `len(orders)` 之和；人工耗时需现场实测（未验证） |

配套的**对照实验**建议（与报告第 2 章同一套"只改一个变量"的做法）：

1. 全打击（不点按钮） / 全前进 / 脚本化切换（`operator_sim.py`）三组，同一想定各跑 N 局；
2. 只改一个变量：切换阈值（何时该藏）、倍速（时延-效果曲线）、是否释放 EMCON；
3. 每组记录：暴露时长、命中率、被瞄准峰值、点击次数与时延分位数。

## 5. 边界（必须写进报告的限制）

1. **`ok:true` = 指令已下发，不等于已生效**。生效要看 `Plat#LuaHistory.log`、单元
   面板或录像；回执只证明 API 调用没抛异常/没返回失败。
2. **不评估威胁、不自动回切**（草图：自动规避 = 否）。"什么时候该切回来"仍然是
   人的判断，这正是本设计要验证的那部分。
3. 文件通道是单机假设（同机两个进程，同一个 `D:/LingYi/exp/button/`）。
4. 与主智能体的地导自卫规则**互斥**：两者同时写雷达/油门会互相覆盖，实验时必须
   关掉 `SamBattalionDefense.ENABLE`。
5. 二态语义在**设施类地面单元**上是否真能机动（`plotted_course` 对设施是否生效）
   在靶机上未验证；若不可动，`move` 模式退化为"关机静默"，报告中需改写该态的
   定义。
