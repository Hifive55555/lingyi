# 报告正文人性化改写方法（往返翻译 + 逐句精校）

本文档记录 `最新报告/paper/` 下 Typst 报告正文的改写流程、工具链、约束与实际效果，供后续继续改写或复用时参照。

- 首次应用：commit `61d207a`（重写 1.2 节、新增 1.3 节）
- 处理对象：该次提交在 `.typ` 文件中新增的正文段落
- 处理结果：35 段、4234 字 → 约 5200 字，`typst compile` 通过

---

## 1. 要解决的问题

原稿有一个稳定的写作习惯：**尽量省略字数**。表现为分句之间靠分号串接、主语承前省略、因果关系用破折号或并列结构隐含、括号里塞进补充说明。这种写法密度高，但代价是可读性差——读者必须自己补上被省掉的连接词，才能还原作者的意思。

改写的目标是：在**不改变事实、数字、术语、结论**的前提下，把被省略的语言成分显式补出来，让每个句子自身成立、句间关系明确。因此改写后的文本必然比原文更长，这不是冗余，而是把原本隐含的信息写出来。

需要强调的是，这不是「扩写」。判断标准是：

- ✅ 补出原文隐含的关系（因果、让步、条件、指代）
- ✅ 展开被压缩的分句，让每个句子有完整的主谓
- ❌ 增加原文没有的信息、推断、举例
- ❌ 用同义词堆叠凑长度

## 2. 方法：为什么用「小模型往返翻译」

直接用大模型润色有个通病：它会按自己的写作习惯重写，产出典型的大模型中文腔——四字短语堆叠、排比句、过度对称的结构。这类文本读起来「流畅」但缺少具体信息，反而比原稿更难读。

往返翻译（round-trip translation）绕开了这个问题：让一个小型**专用翻译模型**把中文译成日文，再译回中文。模型在这一过程中不做「润色」判断，只做翻译，因此：

1. 中文里被省略的语法成分，在日语中**必须显式存在**（日语不能省略主语和格助词）
2. 日文再译回中文时，这些成分会以中文的显式形式保留下来
3. 模型的翻译用词与原始写作习惯不同，AI 腔特征句法被替换

结果是一段语法完整、连接明确、但**没有大模型腔**的中文。这正是需要的效果。

### 为什么选混元 7B

`tencent/Hunyuan-MT-7B` 是专职机器翻译模型（非通用对话模型），符合两条要求：

- 参数规模小（≤9B），在硅基流动平台上免费额度充足
- 只做翻译、不做发挥，遵守「translate without additional explanation」这类指令

**已知弱点**（下节 5.1 详述）：对中文里高度压缩的表述（如「折合」「十条」）和分号串接的多重并列关系，容易误读。这是必须配合精校的原因。

## 3. 工具链

全部在命令行完成，脚本位于 `/tmp/rt/`（临时目录，未纳入版本库）。

### 3.1 占位符保护（`ph.sh`）

改写不得触碰的内容，先替换成占位符 `QQX0XQQ`、`QQX1XQQ`……，译完再原样还原。保护的类别：

| 类别 | 正则 | 例 |
|---|---|---|
| 数学 | `\$[^$]+\$` | `$U_R$`、`$d_0$` |
| 行内代码 | `` `[^`]+` `` | `` `initial()` ``、`` `step()` `` |
| 交叉引用 | `@[A-Za-z][\w:.-]*` | `@fig:arch`、`@tab:score` |
| 标签 | `<[A-Za-z][\w:.-]*>` | `<fig:evade-fsm>` |
| 数值区间 | `\d+[–-]\d+` | `3.3–6.1` |
| 百分数 | `\d+%` | `65.5%` |
| 带单位数字 | `\d+\s*(秒\|分钟\|海里\|km\|倍\|条\|项\|组)` | `180 分钟`、`500 条` |
| 领域术语 | 术语表（约 90 条） | `物理作战域三维监控`、`弹速`、`判据` |
| 裸数字 | 兜底 | `148`、`273` |

术语表内容（`/tmp/rt/term.txt`）需覆盖全篇的固定叫法，包括五个智能体全名、系统组件名、关键判据名。**术语表越密，结果越稳**——因为模型可自由发挥的空间越小。

### 3.2 编码与还原

```bash
# 编码：术语/数值/结构 → QQXkXQQ，同时写出 .map 对照表
./ph.sh enc <原文.txt> <编码.txt>

# 还原：按 .map 替换回原文本
./ph.sh dec <译文.txt> <还原.txt> <原文.txt.map>
```

两个实现要点：

**同一术语复用同一编号。** 首次实现的 bug 是每次 `re.sub` 命中都分配新编号，导致「伪代码」出现两次却是 `QQX0XQQ` 和 `QQX7XQQ`，还原后错位。改为维护「术语 → 编号」字典。

**相邻占位符必须合并。** 例如 `180 分钟折合墙钟 18 分钟` 会生成三个连续占位符 `QQX2XQQ折合QQX3XQQ QQX4XQQ`，模型在三连占位符上会丢项（实测丢了 `18 分钟`）。因此编码后做一次合并：相邻占位符（中间只隔空格/顿号）合并成一个，值取拼接文本。合并后为 `QQX18XQQ = 墙钟 18 分钟`。

### 3.3 双跳翻译（`a.sh`）

```
中文（占位符形式）
  → [分号句号化]  → Hunyuan-MT-7B → 日文
                                    → Hunyuan-MT-7B → 中文
                                                        → 还原占位符
```

**分号句号化**是必要的一步：原稿大量使用分号连接并列项，译为日语时容易把并列关系误读为归属关系。实测「180 分钟折合墙钟 18 分钟；平台决策间隔为 30 秒仿真时间」被误译为「决策间隔属于同一个平台…实际时间 3 秒属于另一个平台」。把 `；` 替换为 `。` 后再送译，该错误消失。

参数：`temperature=1.0`，`max_tokens=5000`。

### 3.4 后处理（`fix.sh`）

占位符还原后，模型常在占位符两侧留空格，形成「程序 推演 会被执行」这类。清理规则：删除**汉字与汉字之间**的空格、删除中文标点前空格，保留中英文之间的空格（Typst 排版需要）。

## 4. 段落切分原则

**处理**：

- 空行分隔的正文段落
- 以 `_强调_` 开头的段落（Typst 中 `_x。_` 是小标题样式）

**不处理**：

- 标题行（`= `、`== `、`=== `）
- `#figure()` / `#table()` 块内部，包括 `caption: [...]`
- 代码块 ` ``` `
- 表格单元格（`[决策], [上百条配置…], ...`）——表格是并列短句，展开会破坏对齐

从 git 取新增段落：

```bash
git show <commit> --format="" -- <file.typ> \
  | grep -E '^\+' | grep -v '^+++' | sed 's/^+//' \
  | grep -vE '^\s*$' | grep -vE '^=|^#|^\s*\)|^\s*image|^\s*caption'
```

## 5. 精校：方法 A 的必需环节

混元的输出是**风格底稿**，不是终稿。必须逐段对照原文修正事实。这一步不能省，也不能交给模型（试过让另一个模型对照原文校正，见 5.2）。

### 5.1 混元的典型误译

实测出现过的偏移，按类型归纳：

| 原文 | 误译 | 类型 |
|---|---|---|
| 失效模式是「漏」 | 问题包括「信息泄露」 | 单字术语被扩解 |
| 二十余条支援任务 | 20 多个支援任务模块 | 约数被具体化 + 单位错 |
| 推演以 10 倍速运行 | 推演的处理速度与 10 倍相同 | 比较关系被误读 |
| 180 分钟折合墙钟 18 分钟 | 180 分钟的处理速度则相当于墙钟 18 分钟 | 分号并列误读为归属（**已用句号化解决**） |
| 三条轴线…三个切面 | 三条轴线…三个相互关联的处理流程 | 比喻被字面化 |
| 本队的取舍 | 本队与取舍之间的关系 | 领属关系被误读 |
| 逐条拆开、逐条对照检验 | 划分为多个部分（即逐条），逐条可以比对 | 动宾结构被拆解 |
| 某区域可以不要 | 哪些区域可以被忽略 | 语气漂移 |
| 机械单独做也不行 | 仅依靠机械设备进行处理也是不够的 | 名词误读为设备 |

**归纳出的规律**：混元在「压缩表述」处最容易出错，具体是约数（二十余）、比喻（切面）、领属（本队的）、单字概念（漏）、动宾短语（拆开检验）。精校时优先检查这些位置。

### 5.2 为什么不做二次模型校正

尝试过方案：混元双跳后，再用 `zai-org/GLM-4.5-Air` 对照原文校准。结果是两个极端：

- 指令强调「以原文为准」→ GLM 直接抄回原文，改写完全消失
- 指令强调「沿用译稿句式」→ GLM 把混元的错误当成事实，还自行编造英文注释、Markdown 列表

原因是 GLM 无法区分「原文的事实」与「译稿的语言组织」，这个区分只有人类读者能可靠完成。因此**精校由人完成**。

### 5.3 精校的检查清单

逐段对照时，按以下顺序核对：

1. **数字**：所有阿拉伯数字、中文数字（二十余、上百、十余）的数量级与单位
2. **术语**：智能体名、组件名、判据名、章节号引用是否原样
3. **逻辑关系**：因果、条件、让步、转折的指向是否与原句一致（最容易在分号处出错）
4. **指代**：「它」「这」「两者」指向的对象是否与原句相同
5. **否定与限定**：「无法」「不必」「仅」「只」的位置是否保留了原句的限定范围
6. **未增加内容**：改写里是否有原文没有的推断（如有，删去）

### 5.4 允许的展开

以下是允许的，属于「把隐含的写出来」：

> 原：而这类错误比「跑不起来」更难发现。
> 改：而这类错误比「跑不起来」更难发现，因为推演照常推进，只是前提已经不是原本想设的那个战场。

原文用「更难发现」已经隐含了「表面上正常」这层意思，展开后读者不必自己推断。

> 原：而两者恰好相反。
> 改：而这两件做不好的事恰好互为反面。

原文「两者」指向模糊，明确指向是必要的澄清。

### 6.2 样例

**原文**

> 这三条轴线不是并列的功能清单，而是人机能力边界的三个切面：在每一条轴线上，人都有一项做不好的事，智能体也有一项做不好的事，而两者恰好相反。本节只说明这种相反为何构成「必须协同」的理由，具体怎么落地留到 1.3 节。

**改写后**

> 需要强调的是，这三条轴线并不是一份并列的功能清单，而是人机能力边界的三个切面。之所以这样说，是因为在每一条轴线上，人都有一项做不好的事，智能体也有一项做不好的事，而这两件做不好的事恰好互为反面。本节只说明这种互为反面为何构成了「必须协同」的理由，至于具体怎么落地，则留到 1.3 节展开。

变化点：

- 冒号改为句号 + 「之所以这样说，是因为」——把因果显式化
- 「两者」→「这两件做不好的事」——补全指代
- 「而两者恰好相反」→「而这两件…恰好互为反面」——消解「相反」的歧义（是方向相反还是性质相反）
- 「具体怎么落地留到」→「至于具体怎么落地，则留到」——补出转折连词

**原文**

> 人单独做决策，失效模式是「漏」与「不一致」。……漏掉其中一条不会报错、也不会中断推演，只会在某个时刻以一次失败的拦截显现出来——这正是人工操作最难自查的一类错误。

**改写后**

> 人单独做决策时，其失效模式表现为「漏」与「不一致」。……在这样的规模下，漏掉其中一条既不会报错，也不会中断推演，它只会在某个时刻以一次失败的拦截显现出来；而这一类错误，恰恰是人工操作最难自查的。

变化点：

- 「既…也…」+「在这样的规模下」——把上文提到的规模与本句的因果关系显式接上
- 破折号改为分号 +「而」——原句的破折号同时承担「解释」与「转折」两种功能，显式化为转折

## 8. 遗留与注意

- **术语表需随内容扩充**。新增章节涉及新术语时，先补 `term.txt` 再跑，否则混元会自行变译。
- **混元温度**：`1.0` 用于正文（保留改写力度），温度更低会更接近直译、改写力度减弱。
- **本流程不适用于表格与图注**。图注是压缩的说明文字，展开会显得啰嗦；表格单元格展开会破坏布局。
