## 1. 它解决什么问题

### 1.1 在智能体流水线里的位置

```
                    ┌───────────────────── 想定编辑智能体（本文）─────────────────────┐
自然语言作战场景  →  │  NL 解析 → 想定规格(IR) → Lua 脚本 → 无头引擎 → .scen → 回读验收 │  → 想定集
                    └───────────────────────────────────────────────────────────────┘
                                                                    ↓
                                              智能体验证 / 训练（Deduction + 规则智能体 / RL）
                                                                    ↓
                                              算法演进、参数调优、场景泛化评测
```

它不做战术决策，只负责**把"想要什么样的战场"变成"引擎认的想定"**，并且保证：

1. **说得清**：自然语言里的每个要素都能落到一条可核对的字段上（有留痕）；
2. **跑得起来**：`.scen` 落盘、引擎可回读、官方框架能推进推演（有冒烟证据）；
3. **可批量**：同一份场景定义能按维度扫出一族变体（兵力规模、距离、朝向、气象、条令、时长……）。

### 1.2 为什么必须是"生成 Lua"而不是"改 .scen"

* `.scen` 是 **XML 外壳 + LZ4（加密/分段）压缩体**，自解实测全部失败（手册 §5）；
* 引擎自己的写入口只有两类：Lua 接口（`executeLua`，273 个 API）和 244 个命名 RPC；
* 想让 AI 自己"新想定/改兵力/加任务/存盘"，唯一稳的通道就是 **Lua**。

所以本智能体的核心产物是**一份可执行、可归档、可复现的 Lua 脚本**，`.scen` 是它的执行结果。

### 1.3 与"人工在 UI 里建想定"的差别

| | UI 手工建 | 本智能体 |
| --- | --- | --- |
| 建一份 10 单元/2 任务的想定 | 10~20 分钟（点选、逐个配挂载/任务区） | **3~5 秒** |
| 建 12 个变体 | 数小时，且极易漏改 | **94 秒**（实测 12/12 通过） |
| 可复现性 | 靠人记 | 规格 JSON + Lua 脚本 + 种子，逐位可复现 |
| 可验证 | 靠眼看 | 17 项自动验收 + 冒烟推演 |
| 需要显示环境 | 需要 | 不需要（无头；只要 Session 1 的窗口站） |

## 2. 总体架构

### 2.1 六层结构

```
        自然语言 / 已有 .scen / 规格 JSON
                     │
   ┌─────────────────▼──────────────────┐
   │ L1 语义层  nlu.py（规则解析器 + 可选 LLM）
   │   · 切句/切段（按推演方）           │  留痕：识别到什么、缺省补什么、哪里没懂
   │   · 槽位抽取（时间/战区/兵力/任务/气象/条令）
   └─────────────────┬──────────────────┘
   ┌─────────────────▼──────────────────┐
   │ L2 规格层  spec.py（ScenarioSpec IR）
   │   · 强类型 dataclass + JSON        │  validate() 在**下发前**拦结构性错误
   │   · 几何算子 translate/rotate/spread/scale_units（族生成的基座）
   └─────────────────┬──────────────────┘
   ┌─────────────────▼──────────────────┐
   │ L3 编译层  lua_gen.py
   │   · 分块脚本（9 块）+ 占位符 %{S:..}/%{U:..}/%{M:..}
   │   · 自包含脚本（local + string.match，可给人看/贴控制台）
   └─────────────────┬──────────────────┘
   ┌─────────────────▼──────────────────┐
   │ L4 执行层  builder.py + lyclient.py + engine.py
   │   · DBID 在线复核（queryDatabase）  │
   │   · 地形合法性（getElevation，落水/落陆吸附）
   │   · 逐条 executeLua，抓 GUID 回填    │
   │   · Command_SaveScen + 等落盘        │
   └─────────────────┬──────────────────┘
   ┌─────────────────▼──────────────────┐
   │ L5 验收层  digest.py + verify.py
   │   · GetScenarioContent → XML → digest
   │   · 17 项 spec vs engine 逐项比对
   └─────────────────┬──────────────────┘
   ┌─────────────────▼──────────────────┐
   │ L6 族层  family.py
   │   · 变量轴取样（网格/随机）         │
   │   · 既有 .scen → digest → spec 复刻  │
   │   · manifest.csv（这一族的自变量）   │
   └────────────────────────────────────┘
```

## 3. 想定规格 IR（`ScenarioSpec`）

### 3.1 为什么要有中间层

直接"NL → Lua"看起来更短，但工程上会立刻失控：

* **错误定位**：Lua 报错说的是"第 37 条语句 `AddUnit` 失败"，规格层能说"红方第 2 个单元的 dbid 在 DB 里不存在"；
* **可校验**：缺任务区、任务引用了敌方单元、经纬度越界……这些能在**下发之前**全部拦住（`validate()` 返回错误列表）；
* **可变换**：族生成本质是对规格做几何/数量变换，而不是对 Lua 做字符串替换；
* **可复用**：同一份规格既能编译成 Lua，也能编译成未来别的平台脚本。

### 3.2 字段表

| 字段 | 类型 | 说明 | 对应引擎调用 |
| --- | --- | --- | --- |
| `title` | str | 想定标题（唯一） | `SetScenarioInfo{TITLE}` |
| `start_time` | str | 作战开始时间（**只写简报，不下发**，见手册坑 #5） | — |
| `duration_s` | int | 推演时长（秒） | `SetScenarioInfo{DURATION}` |
| `complexity`/`difficulty` | int | 复杂度/难度 | `SetScenarioInfo` |
| `description` | str | 简报（纯文本自动包成 HTML，出站时 Base64） | `SetScenarioInfo{DESCRIPTION}` |
| `center` | {lat,lon} | 战区中心（几何算子的原点） | 不直接下发 |
| `seed` | int | 随机种子（参考点 GUID 由 (title, seed) 确定性生成） | `SetScenarioInfo{SEED}` |
| `sides[]` | Side | 推演方：`name` / `posture{对方:码}` / `doctrine{}` / `camera{}` | `AddSide` `SetSidePosture` `SetSideOptions` `SetDoctrine` |
| `units[]` | Unit | 单元：`side` `kind` `name` `dbid` `lat` `lon` `alt` `heading` `count` `loadoutid` `base` `mission` `alias` | `AddUnit` |
| `missions[]` | Mission | 任务：`side` `name` `mtype` `subtype` `zone[]` `units[]` `isactive` | `AddMission` `AddReferencePoint` `SetMission` `AssignUnitListToMission` |
| `weather` | Weather | `temp` / `rainfall` / `cloud` / `seastate` | `SetWeather(t,r,c,s)` |
| `provenance` | dict | 生成留痕：来源文本、解析器、族变量取值 | 不直接下发 |

### 3.3 校验规则（`spec.validate()`）

**硬错误**（拒绝生成 Lua）：

* 没有推演方 / 推演方重名 / 任一推演方没有单元；
* 姿态码非法、或**两两姿态没有双向设全**（引擎要求显式双向）；
* 单元类型非法、dbid 非正整数、经纬度越界、数量 <1、同一推演方内重名；
* 飞机既没高度也没基地（引擎要求二者之一）；
* 任务类型/子类型不在合法枚举、巡逻区顶点 <3 或 >10、任务没有分配单元、任务分到了敌方单元。

**告警**（放行但记录）：单元没分配到任何任务（会原地待机）、别名与引擎类名不完全一致、没有多余任务的检查。

> 实测价值：早期版本 `validate()` 抓出了「任务分到敌方单元」「任务重名」「设施落水」三类问题，
> 都是在**还没碰引擎**的时候就暴露的。

### 3.4 几何算子（族生成的基座）

| 算子 | 语义 | 用途 |
| --- | --- | --- |
| `translate(dlat,dlon)` | 整体平移（单元 + 巡逻区 + 中心 + 相机） | 换战场位置、改变与岸基/基地的距离 |
| `rotate(deg)` | 绕中心旋转（单元航向同步旋转） | 换战场朝向（同一批兵力从不同方向进入） |
| `spread(factor)` | 初始态势相对中心拉开/收拢 | 初始距离/交战强度 |
| `scale_units(factor)` | 按 `count` 缩放兵力 | 兵力规模 |
| `zone_ring(lat,lon,radius,n)` | 生成规则多边形巡逻区 | 任务区 |
| `new_guid(salt)` | 由 `(title,seed,salt)` 确定性 UUIDv5 | 参考点 GUID 可复现 |

## 4. 自然语言 → 规格（`nlu.py`）

### 4.1 设计选择：规则解析器为默认，LLM 为可选

| | 规则解析器（默认） | LLM 通道（`--parser llm`） |
| --- | --- | --- |
| 依赖 | 无（离线、无 key） | OpenAI 兼容接口（`SCE_LLM_BASE/KEY/MODEL`） |
| 确定性 | 完全确定（同文同规格，连 GUID 都同） | 有温度、需要校验 |
| 可解释 | 逐条留痕（识别/缺省/未懂） | 要额外让模型解释 |
| 覆盖 | 词表内的要素（平台/战区/任务/气象/方位/数量） | 长尾表达更强 |

工程上把两者做成**同一个出口**（都产出 `ParseResult{spec, log, unparsed}`），
LLM 输出一律再过一遍 `spec.validate()` + 规则解析补全（缺巡逻区/缺姿态时用规则结果兜底）。
这样"换个模型"不会改变下游任何东西。

### 4.2 规则解析器的五步

```
① 规范化      全角→半角，标点归一（注意：句号同时是小数点，切句要用
              (?<!\d)\.(?!\d)，否则 24.48 会被切成 24 / 48 —— 实测踩过）
② 全域抽取    标题 / 时间 / 时长 / 战区或显式经纬度 / 复杂度 / 难度 / 气象 / 条令
③ 按方切段    一句里常塞多方（"红方 2 艘052D 在西侧，蓝方 2 艘伯克级在东侧"），
              按"最近的前置推演方关键词"切段；整句没提推演方则继承上一句
④ 兵力槽位    最长别名优先匹配（052DL 先于 052D）；数量词支持"2 艘/两艘/052D×2/2 个"；
              几何：方位词（东西南北/东北…）+ 海里 → 锚点；显式"北纬X、东经Y"只给紧邻的
              **固定设施**用，机动单元仍走方位+距离；高度给飞机
⑤ 任务槽位    任务关键词 + 子类型词表（14 种中文→引擎子类型）；
              巡逻半径；同方同类任务重复描述则合并；没写任务的一方按兵力构成补默认任务
```

## 5. 规格 → Lua（`lua_gen.py`）

### 5.1 两种等价产物

| 产物 | 形态 | 用途 |
| --- | --- | --- |
| `LuaProgram.blocks` | 9 块：`info / sides / setup / weather / units / missions / zones / assign / save`，块内引用写 `%{S:红方}` `%{U:舰名}` `%{M:任务名}` 占位符 | **执行**用：逐条下发、逐条抓 GUID、错误定位到单条 |
| `LuaProgram.script` | 自包含脚本：`local S_1 = AddSide(...)`、`local M_1G = string.match(M_1, "guid = '([^']+)'")` | **归档/人读/贴控制台**用 |

自包含脚本头部写清来源、时间、规模，例如：

```lua
-- ============================================================
-- 想定：东海反舰遭遇战
-- 生成：sce_agent（想定编辑智能体）  2026-11-17 20:31:12
-- 保存路径：D:/LingYi/Data/Scenarios/EXP1-东海反舰遭遇战.scen
-- 规模：单元 5 型 / 10 个；任务 2 个；参考点 8 个
-- ============================================================
```

### 5.2 生成规则全部来自实测（不是猜的）

| 规则 | 依据 |
| --- | --- |
| `NewScenario` 必须是第一条 | 无场景时读写接口会把引擎搞崩 |
| `DESCRIPTION` 单次 Base64（内容是 HTML 简报） | 传原文 → 乱码 |
| `SetSidePosture` **双向**都发 | 只发单边 → 引擎里默认"不友好"，AI 不开火 |
| 每个推演方都发 `SetSideOptions{CAMERA*}` | 否则该方推演界面黑屏；高度按战场跨度自动算 |
| `SetDoctrine` 两参数形态（`{side=X},{条令表}`） | 合并成一个表 → 无效 |
| 飞机一律带 `loadoutid`，无方案时用 `3` | 缺键 → `缺少挂载！`；`0` → 能建但**编不进任务** |
| `AddMission` 只发 `isactive/type/unloadMount*` | `patrolZone`/`waypoints` 被静默忽略 |
| 巡逻区 = `AddReferencePoint`（UUID 由生成端确定性给出）+ `SetMission{patrolZone}` | 唯一有效路径 |
| `AssignUnitListToMission(单元GUID列表, 任务GUID, false)` | 三参缺一不可 |
| `Command_SaveScen` 给完整 Windows 路径 | 返回相对路径 `Scenarios/x.scen` |
| **不下发 `STARTTIME`** | 一下发，推演第 1 步就结束（`sim_time≈2.26e7 s`） |

### 5.3 确定性

参考点 GUID = `uuid5(NAMESPACE_URL, "标题|seed|zone|任务名|序号")`，
所以**同一份规格 + 同一个 seed，重复生成得到逐位相同的 Lua**（实验里 V02 重建两次的 GUID 完全一致）。
这对"同一想定上对比不同算法"很重要：随机性必须能钉住。

## 6. 执行层（`builder.py`）

### 6.1 六步流水线

```
spec ─┬─① validate()            硬错误直接拒绝，不下发
      ├─② check_dbids()        queryDatabase 复核每个 (kind,dbid)；设施探高程，落水/落陆则同心环吸附
      ├─③ generate()           spec → 分块 Lua
      ├─④ exec                 逐条 executeLua；sides/units/missions 块用**返回值**抓 GUID
      ├─⑤ save+readback        Command_SaveScen → 轮询文件大小 → GetScenarioContent → digest
      └─⑥ verify + archive     17 项比对 → verify.md；写 spec/lua/build/digest 四件套
```

### 6.2 GUID 捕获（关键细节）

* `AddSide` / `AddUnit` 返回**纯 GUID**（`count>1` 时返回逗号分隔的多个）；
* `AddMission` 返回 `mission {guid = 'X',name = 'Y'}` → 正则取 GUID；
* `AddReferencePoint` 的 GUID 是**我们自己生成的**，不需要回读；
* `GetMissions()` **不可用**（空参报错、带方名直接把 RPC 拖到超时，引擎被打僵），
  所以任务 GUID 只能靠 `AddMission` 的返回值 —— 这也是"必须逐条下发"的直接原因。

### 6.3 物理合法性自愈

| 情况 | 处理 |
| --- | --- |
| 设施落在水面（`getElevation<=0`） | 同心环搜索（0.03° 步长、16 方向、最多 12 环）找最近陆地并移动，记一条 note |
| 舰船/潜艇落在陆地 | 同上找最近海面（0.05° 步长、最多 16 环） |
| 都找不到 | 抛错并说明"请直接给陆地/海面坐标" |

实测：`04-台海联合火力打击` 里 S-400 的原始坐标 `(24.48, 118.08)` 在厦门外海，被自动吸附到陆地后仍通过验收。

### 6.4 与官方框架的互斥

官方框架（`Deduction`）在启动/退出时按进程名清理 `Plat.exe`，会杀掉建想定引擎（实测两次）。
所以 CLI 里 `--smoke` 的顺序是：**建完 → 停全部引擎 → 冒烟 → 重新拉起引擎**。

## 7. 验收层（`digest.py` + `verify.py`）

### 7.1 为什么必须回读

引擎对很多"不该接受"的参数**不报错**：`SetDoctrine` 回 `code=0` 但不生效、`SetMission` 的
`patrolZone` 对 Strike 无效、`loadoutid=0` 的飞机静默地从任务里掉出去。
不下发后再读一遍，等于闭着眼睛建想定。

### 7.2 17 项检查

| # | 检查 | 判据 |
| --- | --- | --- |
| 1 | 文件已落盘且非空 | 靶机文件大小 > 0 |
| 2 | 引擎可回读 | `GetScenarioContent` 返回 code=0 且 >200 字节 |
| 3 | 标题一致 | 字符串相等 |
| 4 | 推演时长一致 | `Duration/1e7 == duration_s` |
| 5 | 推演方集合一致 | 名称集合相等 |
| 6 | 两两对抗关系正确 | 双向、码值 N=0 F=1 U=2 H=3 |
| 7 | 兵力数量分布一致 | 每方每类平台数 |
| 8 | 单元齐全 | 按 (推演方, 名称) 匹配 |
| 9 | 单元 DBID 正确 | 相等 |
| 10 | 单元初始坐标正确 | ±0.002°（≈200 m） |
| 11 | 任务齐全 | 按 (推演方, 名称) |
| 12 | 任务类型/子类型正确 | 归一化后相等（AIR→AAW 等） |
| 13 | 巡逻区顶点数正确 | 仅 Patrol 硬校验 |
| 14 | 单元-任务分配数正确 | 按**平台**计（count>1 展开） |
| 15 | 没有多余任务 | 告警级 |
| 16 | 条令关键字段一致 | **告警级**（引擎本版本不持久化，见手册坑 #17） |
| 17 | 气象一致 | 温度/降雨/云量/海况 |

### 7.3 冒烟推演（"确定能跑"的硬证据）

`smoke.py` 把一段 runner 投到靶机，用**竞赛同款链路**（`Deduction`）加载想定、推进 N 步、取 `BatResult`：

```json
{"scenario": "EXP1-东海反舰遭遇战", "reset": 1, "steps": 30,
 "sim_time": 150.463, "result": 0, "error_side": "", "red_score": 0, "blue_score": 0}
```

判据：`reset==1`（想定被正常加载）、`steps>0`（推演在推进）、`sim_time ≈ steps × 决策间隔`（时钟正常）、
`error_side` 为空（没有一方报错）。附件里的 8 个想定全部通过。

> 反例很有说服力：早期有 `STARTTIME` 的想定冒烟结果是 `steps=1, sim_time=22592662`——
> 一眼就能看出"时钟被搞坏了"。这也是我们坚持把冒烟做进流水线的原因。

## 8. 知识库（`catalog.py` + `data/`）

| 数据 | 规模 | 来源 | 用途 |
| --- | --- | --- | --- |
| `aliases.json` 平台别名 | **85 条** | 人工整理 + 引擎复核 | 中文说法（052D / 歼-20 / 伯克级…）→ `(kind, dbid)` |
| `db_catalog.json` 全量平台目录 | **13 203 条**（舰 3 532 / 机 5 494 / 潜 672 / 设施 3 365 / 卫星 140） | `queryDatabase` 全量扫描（100 秒） | 语义检索（"找反潜巡逻机"）、别名兜底解析 |

而外部文档写的是 052D）。

## 9. 同类想定集（`family.py`）

### 9.1 变量轴（9 个，都是纯函数 `f(spec,value)->spec`）

| 轴 | 语义 | 典型取值 |
| --- | --- | --- |
| `force_scale` | 兵力规模系数 | 0.5 / 1 / 2 |
| `spread` | 初始态势拉开系数 | 0.8 / 1.2 / 1.6 |
| `rotate` | 战场绕中心旋转 | 0 / 45 / 90 / 135 |
| `duration_h` | 推演时长（小时） | 1 / 2 / 4 |
| `seastate` | 海况等级 | 1 / 4 / 7 |
| `wcs` | 武器控制状态 | free / tight / hold |
| `zone_radius` | 巡逻区缩放 | 0.6 / 1.0 / 1.5 |
| `offset_nm` | 战场整体东移（海里） | 0 / 50 / 100 |
| `seed` | 随机种子 | 若干 |

* `--n 0`：取**网格**（笛卡尔积）；`--n K`：按 seed **随机取样** K 个（去重）。
* 每个变体都独立走完整流水线（建 + 验收），并写 `family_<标题>.csv` 记录**自变量与结果**，
  这份 CSV 就是"这一族想定扫了哪些维度"的凭证。

### 9.2 两条生成路径

**A. 规格出发**（自然语言 → 规格 → 族）：

```bash
python cli.py family out/EXP1-东海反舰遭遇战/spec.json \
    --axis force_scale=0.5,1,2 --axis rotate=0,45 --axis seastate=2,5     # 3×2×2 = 12 个变体
```

**B. 既有想定出发**（`.scen` → 结构复刻 → 族）：

```bash
python cli.py family-from-scen '诺曼底2027(人机协同-人机版V0.2.7)' --axis force_scale=0.5,1,2
```

复刻（`spec_from_digest`）保留：推演方与姿态、条令、气象、单元（型号/位置/朝向/高度/挂载角色）、
任务（类型/子类型/巡逻区坐标/参与兵力）；丢弃：挂载明细、事件脚本、编队、消息日志。
**这是"结构复刻 + 参数扰动"，不是二进制复制**——对算法评测来说，这正是想要的"可控变量集"。

复刻保真度实测（诺曼底）：

| 源想定 | 复刻规格 | 说明 |
| --- | --- | --- |
| 251 平台 / 2 方 | 249 单元（2 方） | 2 个设施落在水面，被吸附/合并 |
| 40 个任务 | 25 个 | 15 个因"巡逻区顶点 <3"或"无分配兵力"被跳过 |
| 180 参考点 | 100 个巡逻区顶点（25 任务 × 4） | 每任务重建 4 点菱形区 |

## 11. 在智能体验证 / 训练流水线里的用法

### 11.1 场景类别覆盖（泛化评测）

`--axis` 的组合就是"评测面"：同一算法在 `force_scale × rotate × seastate` 上的表现差异，
可以拆成"兵力敏感性 / 方位敏感性 / 气象敏感性"。CSV 里的 `variant → 自变量 → 验收结果` 就是实验台账。

### 11.2 与训练框架对接

生成的 `.scen` 直接放进 `D:\LingYi\Data\Scenarios\`，框架侧只需要改想定名：

```python
# D:\LingYi\intelligent\ai\agent\config.py → get_server_config()['game_server']['simulate']
{"scenario": "EXP1-东海反舰遭遇战", "episodes": 100, "compression": 10001,
 "decision_interval": 5, "testing": False, "save_result": True, "load_scenario": True}
```

`smoke.py` 用的就是这条链路，所以"冒烟通过"≈"可以进批量训练/评测"。

### 11.3 参数调优的用法

同一个想定族 + 同一个智能体 + 不同参数 → `gamedata.db` 的 `batrecord` 表；
因为想定是**由种子确定的**（GUID 都一致），不同参数跑的是**同一战场**，对比才有意义。

## 12. 已知限制与下一步

| 限制 | 影响 | 下一步 |
| --- | --- | --- |
| `STARTTIME` 不能下发（会毁掉时钟） | 想定的"作战时间"只存在于简报里，引擎用默认时钟 | 试试命名 RPC `setScenarioInfo{startTime}` 或换引擎版本 |
| `SetDoctrine` 不持久化 | 条令差异在回读里看不到（下发仍保留） | 逐条验证 `setDoctrine` RPC（protobuf 版本） |
| `Strike` 任务无巡逻区、无目标不行动 | 打击类场景退化为等价 Patrol | 用 `AssignUnitAsTarget` 预置目标清单 |
| 复刻丢 15/40 个任务（诺曼底） | 结构复刻不完整 | 支持"任务区缺顶点时按兵力重心补一个 4 点区" |
| 单引擎串行 | 1000 变体 ≈ 2 小时（按 7 s/个） | 多端口并行（引擎支持 21001–21500 端口对），已在 `EngineManager` 留了参数 |
| 挂载库只覆盖 156 机型 | 部分机型用通用 `3`（无武装） | 用 `loadout probe` 批量探测 DB 的 `WeaponLoadout` 表 |
| 自然语言覆盖 | 词表外的表达会走默认值并记 `unparsed` | LLM 通道 + 解析结果回归测试集 |
